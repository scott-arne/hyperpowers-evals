The nightly `ingest-orders` failure is a clock mismatch. `pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time) and `pipeline/writer.py` dedupes with `datetime.utcnow()`. During the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice and the unique index raises `DuplicateKeyError`.

I recommend switching the orchestrator to UTC. The edit is one line, but 23 modules import `orchestrator.py` and the window changes for all of them, so it needs the full suite (about 25 minutes). The other option, deduping on local time in the writer, keeps the change inside one module but keeps local time in the pipeline, which the team has wanted out since the DST incident in March.

One check is still open. I did not confirm whether any of the 23 importers depend on the window being local time; that is about an hour. I would do it before merging the UTC change.

A second defect hid this one. `utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`, so the writer's failures were swallowed and logged at DEBUG, and the first duplicate was invisible until the index rejected it. I would change the default to `raise_on_exhaust=True` in a separate PR: 14 call sites use the current default and several may depend on the swallow, so each site needs checking before the default changes.

I ruled out the schema checks. The two of them, in `config/loader.py` and `pipeline/writer.py`, check the same thing, and neither is involved. The CI step that blocks deploy on a schema snapshot diff passed on every failing night.

Reproducing it locally took about 40 minutes of harness work first: `tests/conftest.py` pinned an old `freezegun` that broke under Python 3.12. I fixed the pin locally; the full suite will not run on 3.12 without it, so that fix should go in with or before the UTC PR.
