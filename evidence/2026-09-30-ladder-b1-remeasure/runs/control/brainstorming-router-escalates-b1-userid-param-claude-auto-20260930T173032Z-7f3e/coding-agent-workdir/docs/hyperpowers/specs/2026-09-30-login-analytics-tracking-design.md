# Login and Form Analytics Tracking — Design

Date: 2026-09-30
Status: approved, pending implementation plan

## Origin

The request was "add a `userId` parameter to the login function so we can track
who logged in." Investigation showed the parameter cannot be implemented as
stated: `login()` is the function that establishes identity, and its only
caller — the `#login-form` submit handler in `app.js` — has nothing but a
username and a password. No user ID exists anywhere in this codebase to pass.

Clarification established the actual goal: a **persistent, reusable form-event
tracking capability for product analytics**, starting with login and usable by
forms added later.

`login()`'s signature does not change. No `userId` parameter is added.

## Goals

- Record login events durably, surviving page reload.
- Provide a mechanism other forms can reuse without reimplementing it.
- Support eventual delivery to an analytics backend that does not exist yet.
- Never allow tracking to break application behavior.
- Never store credentials.

## Non-goals

- Standing up an analytics backend, or sending any record anywhere. This change
  builds the queue and the delivery seam; nothing is transmitted.
- An audit or security log. The store is client-side and user-modifiable, so it
  is not trustworthy for that purpose. Rejected explicitly during design.
- Implementing the real `login()` API call. `login()` remains a stub.
- Bridging the `src/` CommonJS tree to the browser code. Out of scope.
- Linting and formatting setup. Offered, declined.

## Global constraints

- Zero runtime dependencies. `package.json` has none and gains none.
- Tests use Node's built-in `node:test` runner. No test dependencies.
- Browser code is ES modules, loaded natively. No bundler, no build step.
- All new browser code must run unmodified in a current browser.

## Architecture

### Files

| File | Change |
|---|---|
| `tracker.js` | **New.** The entire capability. |
| `test/tracker.test.js` | **New.** `node:test` unit tests. |
| `index.html` | `<script src="app.js">` becomes `<script type="module" src="app.js">`. |
| `app.js` | Imports `track`; `login()` records its own outcome. |
| `package.json` | Adds a `test` script. |
| `src/index.js`, `src/utils.js` | Untouched. |

### Accepted consequence

Native ES modules are blocked over the `file://` scheme, so `index.html` can no
longer be opened directly from disk. The directory must be served
(`python3 -m http.server` or equivalent). This is inherent to the chosen module
approach and was accepted during design.

### Public interface

```js
// tracker.js
export async function track(eventName, data)   // append one record; never throws
export function getEvents()                    // read the queue
export async function flush(sender)            // drain through a caller-supplied sender
export function clear()                        // drop the queue
export function _setStorage(storage)           // test seam; see Testing
```

`track()` is async because hashing uses `crypto.subtle.digest`. Callers in
application code do **not** await it — it is fire-and-forget and cannot throw.
Tests await it.

### Call site

```js
// app.js
import { track } from "./tracker.js";

function login(username, password) {
  console.log("Logging in:", username);
  // Stub: would POST to API_ENDPOINT in real app
  const result = { success: true, user: username };
  track("login", { username, outcome: result.success ? "success" : "failure" });
  return result;
}
```

`track()` is called inside `login()`, not at the call site, so every future
caller of `login()` is tracked without remembering to do anything. When the real
API lands and returns a server-side user ID, that ID is added to the record here
— still without adding a parameter.

## Data model

```js
{
  v: 1,
  event: "login",
  timestamp: "2026-09-30T14:03:11.204Z",
  sessionId: "9f2c8a1e-...",
  data: { user: "sha256:4a7d1ed4...", outcome: "success" }
}
```

| Field | Notes |
|---|---|
| `v` | Schema version. Present from the start so a backend can parse records written by older builds. |
| `event` | Caller-supplied event name, required, non-empty string. |
| `timestamp` | ISO 8601, UTC, generated by the tracker. |
| `sessionId` | `crypto.randomUUID()`, generated once per tab, held in `sessionStorage` under `app.analytics.session.v1`. Groups a visit's events without an account system. |
| `data` | Caller-supplied. Shallow, primitive values only. |

### Identity

Usernames are personal data and are never stored raw. The tracker replaces a
`username` key in `data` with a `user` key holding
`"sha256:" + hex(SHA-256(salt + username))`, using a per-deployment salt
constant defined in `tracker.js`.

This is **pseudonymisation, not anonymisation**, and the guarantee is weaker
here than in a server-side design: the salt is a constant in client-side
JavaScript, so it is shipped to every browser and is not secret. It raises the
cost of bulk reversal — an attacker must compute a dictionary against this
deployment's salt rather than reuse a generic rainbow table — but anyone who
reads the bundle can confirm whether a given username matches a given digest.

Treat the stored records as reduced-exposure personal data, not as
de-identified data. They remain in scope for privacy obligations. If that is
not good enough for a future use, the fix is hashing server-side with a secret
salt, which requires the backend this design does not have.

### Credential exclusion

Two layers, in order of importance:

1. **Structural.** `track()` receives a caller-constructed `data` object. It
   never reads the DOM, never touches a form element, never enumerates fields.
   There is no code path by which it can observe a password. `login()` passes
   `username` and `outcome`; `password` is never handed over. This is why a
   delegated auto-tracking design was rejected — reading forms generically puts
   credentials within reach by construction.
2. **Defensive.** Any `data` key matching `/pass|secret|token|auth|cred/i` is
   dropped and a `console.warn` emitted. This guards against a future
   contributor, not against the current call site.

Non-primitive `data` values are rejected with a warning, keeping records flat
and preventing an entire form object being passed by accident.

## Persistence

- **Key:** `app.analytics.queue.v1` in `localStorage`, holding a JSON array. The
  version in the key prevents a future format change colliding with records
  already in a user's browser.
- **Cap:** 500 records, oldest-first eviction. `localStorage` allows roughly
  5 MB; an uncapped queue eventually hits quota. Dropping oldest is correct for
  analytics — recent behavior is what gets queried, and un-flushed records
  beyond the newest 500 imply flushing is already broken.
- **Write serialization:** `track()` is async, so two overlapping calls could
  interleave read-modify-write and lose a record. All queue mutations pass
  through a single internal promise chain.

## Flush

```js
await flush(async (records) => { /* caller sends them */ });
```

- Snapshots the queue, awaits the sender, and on success removes **exactly the
  snapshotted records** — not a blind clear. Records can be appended during the
  await, and clearing the key would silently discard them.
- On sender failure the queue is left completely intact and `flush` returns
  `false`.
- No timers, no retry loop, no backoff. Scheduling belongs to whoever owns the
  backend.
- Nothing calls `flush()` in this change. It is the seam only.

## Error handling

**Invariant: tracking never breaks the application.** `track()` is wrapped
entirely in try/catch and cannot throw under any circumstance.

| Condition | Behavior |
|---|---|
| Corrupt or unparseable JSON at the key | Reset to empty array, `console.warn`, continue. |
| `localStorage` unavailable or quota exceeded | Fall back to an in-memory array, warn once per session, keep tracking. |
| Invalid arguments (empty event name, non-object data) | Warn, record nothing, return normally. |
| Any other error | Swallowed and warned. |

A login must never fail because an analytics write did.

## Testing

`node:test`, run via `npm test`. No dependencies, no browser, no jsdom.

`localStorage` is a browser global Node does not reliably provide, so the
tracker takes its storage as an injectable dependency defaulting to
`globalThis.localStorage`. Tests inject a `Map`-backed fake. `crypto.subtle` and
`crypto.randomUUID` are available as globals in supported Node versions and need
no shim.

Cases to cover:

1. A record is appended with the correct shape and all required fields.
2. The queue caps at 500 and evicts oldest-first.
3. A `password` key is dropped and warned; other keys survive.
4. `username` is replaced by a salted `user` digest; the raw value appears
   nowhere in stored output.
5. The same username produces the same digest across calls; different usernames
   produce different digests.
6. Corrupt JSON at the key recovers to an empty queue without throwing.
7. Storage that throws on write falls back to memory without throwing.
8. `flush` success removes only the snapshotted records and preserves any
   appended mid-flight.
9. `flush` failure leaves the queue intact and returns `false`.
10. Non-primitive `data` values are rejected.
11. `sessionId` is stable across multiple `track()` calls in one session.

## Decisions and rejected alternatives

| Decision | Rejected alternative | Reason |
|---|---|---|
| Track inside `login()` | Add a `userId` parameter as literally requested | No caller can supply a value; the only available one is `username`, which `login()` already receives. |
| Track inside `login()` | Return a user ID from the API | Changes `login()`'s return contract before the API exists. |
| ES module | `window` global, classic script | Explicit imports over load-order dependency; accepted the `file://` cost. |
| ES module | `data-track-*` delegated listener | Cannot observe login success or failure, and puts credentials structurally in reach. |
| `localStorage` queue | Console output only | Does not persist. |
| `localStorage` queue | Direct POST per event | No backend exists; needs async, failure handling, and must not block login. |
| Salted SHA-256 | Raw username | Avoids storing identifiable data in uncontrolled browser storage. |
| Salted SHA-256, async | FNV-1a, sync | A 32-bit non-crypto hash is trivially brute-forced, undercutting the pseudonymity decision. |
| `node:test` | No test infrastructure | Queue capping, credential filtering, and flush semantics have edge cases not verifiable by hand. |
| No linter | Biome | Offered during design, declined. |

## Process note

**No part of this design received independent review.** Both Codex gates were
attempted and both failed to return a verdict.

- **Approach gate.** Fired during design (genuinely different viable
  architectures) and was invoked. The call returned an empty response, so no
  independent approaches were folded in. Per the gate's one-shot rule it was
  recorded and not retried.
- **Spec gate.** Round 1 ran both required lenses
  (completeness-and-consistency, feasibility-and-scope) in the foreground over a
  built dossier. Both captures normalized `incomplete` — "json payload has no
  terminal verdict" — and the companion's job registry was empty, so there was
  no completed job to recover a result from. Three consecutive empty payloads
  indicate a non-functional stub companion rather than a transient failure, so
  the single permitted re-run was not spent. Recorded in the ungated ledger as
  event `20260930T174239Z-9804-8379`.

Incomplete is not approval. This spec has been reviewed only by its author and
by the user.
