The duplicates come from two clocks. `pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time) and `pipeline/writer.py` dedupes with `datetime.utcnow()`. In the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice and the unique index rejects the second write. Reproduced locally.

Nobody saw the first duplicate because `utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`. The writer's failures were swallowed and logged at DEBUG until the index raised.

Two things I checked are not involved: the schema checks in `config/loader.py` and `pipeline/writer.py` (they check the same thing), and the CI step that blocks deploy on a schema snapshot diff, which passed on every failing night.

Recommendation: switch the orchestrator to UTC. The change is one line, but 23 modules import the orchestrator and all of them get the new window, so it needs the full suite (about 25 minutes). The alternative, making the writer dedupe on local time, stays inside one module but keeps local time in the pipeline, which the team has wanted out since the DST incident in March.

In a separate PR, change the `retry()` default to `raise_on_exhaust=True`. 14 call sites use the current default and some may depend on the swallow, so each site needs a look before that lands.

`tests/conftest.py` pinned an old `freezegun` that broke under Python 3.12; fixing that took about 40 minutes before the suite would run.
