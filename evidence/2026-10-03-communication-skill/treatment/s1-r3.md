The duplicates come from two clocks. `pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time) and `pipeline/writer.py` dedupes with `datetime.utcnow()`. In the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice and the unique index rejects the second write. I recommend switching the orchestrator to UTC.

Nobody saw the first duplicate because `utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`. The writer's failures were swallowed and logged at DEBUG, so the job only failed once the index rejected a row.

Two fixes for the clock mismatch:

(a) Switch the orchestrator to UTC. One line, but 23 modules import the orchestrator and the window changes for all of them, so it needs the full suite (about 25 minutes).

(b) Make the writer dedupe on local time. The change stays inside one module, but local time stays in the pipeline, which the team has wanted gone since the DST incident in March.

I have not checked whether any of the 23 importers depend on the window being local time. That check is about an hour and is the one open risk on (a).

In a separate PR I would change the `retry()` default to `raise_on_exhaust=True`. 14 call sites use the current default and several may depend on the swallow, so it needs its own review.

Schema is not the cause. The CI step that blocks deploy on a schema snapshot diff passed on every failing night, and the two schema checks (`config/loader.py` and `pipeline/writer.py`, which check the same thing) are not involved.

Reproducing locally took about 40 minutes of setup first: `tests/conftest.py` pinned an old `freezegun` that broke under Python 3.12, and the suite would not run until that was fixed.
