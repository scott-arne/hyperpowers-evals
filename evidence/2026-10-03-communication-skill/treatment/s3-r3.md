The two I would push on hardest are the stateless assumption in 4 and the rollout in 6. The rest are smaller.

Six of the nine formats have not been checked for state, and the migration script assumes none of them keep any. If one has a module-level cache or a parser instance shared across calls, moving it unchanged breaks it, and since all nine land in one PR the break arrives mixed in with eight other moves. Check the remaining six before writing the PR, or have the script refuse to move a module that has mutable state at module level. Either is cheaper than finding it in review.

The flag in 6 defaults to the old path, so unless something runs with it on, the two weeks produce no evidence. Name what exercises the new path during the window (CI with the flag on, one environment, a replay of recent imports through both paths with a diff of the written rows) and the condition for removing the flag. While both paths exist, every format bug fix lands twice, so the window should be as short as that evidence allows.

Registration in 2 has two known ways to fail and the note names one. Discovery by importing the package is the part frozen binaries handle worst, which is why 7 exists; the test runner's import isolation is the other. An explicit list in `plugins/__init__.py` that imports each plugin by name removes the discovery step, works in the frozen binary without a build change, and gives the test runner one import to control. The decorator adds little over that. Check this before spending the day on 7, because it may remove 7.

Also decide what happens when one plugin raises on import. If core sees eight formats and reports the ninth as unknown, a traceback has turned into a user-facing "unsupported format" with no cause attached. Failing the import of the package is the better behavior.

Ignoring unknown keys in 5 keeps old call sites working, and it also means a misspelled option on a new call site does nothing and nobody is told. Accept the known keys and warn on the rest. With `options: dict`, each of the nine plugins also parses its own options, so expect nine copies of that code. A `validate_options` hook that core calls, or a small dataclass per plugin, keeps it in one place.

In 3, when the plugin passes a row and core rejects it, the user sees a schema error with no format context. Decide which layer produces the message. Also say whether core's schema check is the validation that exists today or new code; if new, it is a second thing the PR adds, and the one that costs per row on every import.

The build change in 7 blocks everything else and has the least certain estimate. Do it first as its own PR with a timebox, or confirm the explicit-registry approach makes it unnecessary.

Two things the team will ask that the note does not say: the plugin interface (what a plugin must implement beyond taking `options`), and whether the migration script moves each format's tests along with its code, since that is where the ownership question comes from.
