Ranked by how much I'd worry about each, highest first.

**1. The note treats the migration as mechanical, and it isn't yet.** Three things undercut "moves each format's code without changing it":

- Stateless is checked on 3 of 9. That assumption carries the whole plan. If any of the other six has module-level state (a compiled-regex cache, a counter, a lazily-built lookup table, a class attribute something mutates), import-time registration changes when that state is created and whether it's shared across runs. Check all nine before writing the migration script, not after. A grep for module-level mutables and `global` per format section gets you most of the way.
- Nine formats in one file almost certainly share helpers: date parsing, encoding sniffing, field coercion. "Everything format-specific moves" either leaves those in core (so core isn't small) or copies them into each plugin (so they drift). Say which. An `importers/common.py` is the usual answer.
- The moment code goes behind a plugin API its signature changes, so it is not "unchanged." That's fine, but then the per-format tests have to prove equivalence, which bears on your first open question.

**2. The plugin contract isn't in the note, and it's the thing the team should actually review.** core/plugins/decorator is the easy part. What does a plugin expose: `parse(stream, options) -> Iterable[Row]`, or separate map and validate hooks? Does it stream or does core materialize? When a plugin raises halfway through a file, does core's write path roll back, stop, or skip the row? Those answers decide whether the migration is a day or a month. Write it as a Protocol before anything else.

**3. Drop import-time discovery. Keep the decorator.** Discovery is what makes item 7 a build problem, makes your second open question a real risk, and lets a module imported twice under different names register twice. If `plugins/__init__.py` imports the nine modules explicitly, all three go away: nothing for the freezer to walk, deterministic under test isolation, and one line per new format, which is no worse than "another branch in core" and a lot more honest. Item 7 probably shrinks to nothing. If you keep discovery anyway, the import-isolation question is a blocker, not an open question; it's a thirty-minute spike and it goes first.

Either way: two plugins registering the same format name should raise. Last-wins is a silent regression waiting six months.

**4. The rollout undercuts the design.** The point of plugins is that formats move independently; item 6 then moves all nine in one PR behind one flag. Push on:

- A flag that defaults to the old path means nobody exercises the new path unless someone deliberately flips it. Who, where, on which data? "Two weeks" is a calendar, not an exit criterion. Say what has to be true to flip the default.
- One flag for nine formats means you can't roll one back. A broken format flips everything.
- The old path is the entire old core.py kept alongside the new one, so every bugfix in the window lands twice.

Alternative: core plus the ugliest single format in the first PR, flagged per format. That proves the contract and the shared-helper split on real code before the other eight are committed to it, and each PR after is small enough to review properly.

**5. `options: dict` ignoring unknown keys is a time bomb.** It keeps old call sites working, which is the goal, but a typo'd or renamed option now silently does nothing. Warn on unknown keys at minimum, or time-box the shim to the flag window. A per-plugin dataclass or TypedDict is better, and the migration is the one time you'll be touching every call site anyway.

**6. Double validation is only as good as the split.** "A bad plugin cannot write a bad row" holds if core's schema rules are complete on their own. Today validation is one block; sorting it into format rules and schema rules is a judgment call, and a rule that lands on the wrong side either gets lost or gets duplicated and drifts. Enumerate the current rules and tag each one before moving them. Also decide which error the user sees when both layers reject the same row.

**7. Smaller:**

- Item 5 covers options compat but not import-path compat. Grep for `from importers.core import` outside the package before deciding what stays re-exported.
- Tests move with the plugin, in the same PR. Otherwise item 4's claim is unverifiable.
- "Probably a day" for frozen-binary plus dynamic imports is the classic one-day estimate. Time-box it; point 3 is the fallback.

If you change two things before sending: write the plugin interface down, and do core plus one format first.
