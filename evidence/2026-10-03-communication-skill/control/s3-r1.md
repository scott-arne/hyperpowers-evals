Ordered by what I'd push on hardest.

**4 is the one that worries me.** "Assumed stateless, checked three of nine" means six formats move on hope. The script "moves code without changing it", but code living in core today reaches module-level state and shared helpers for free; once it is in its own module it either can't, or it imports them across the plugin boundary, which is a change. Before the PR, go through all nine for module-level mutables, caches, compiled-regex tables, and helpers two formats share. Anything shared needs a home decided before the script runs, not after.

**2 and 7 are the same problem, and I'd drop both.** Decorator-at-import discovery is exactly what freezers and test isolation break: a plugin that fails to import vanishes silently instead of erroring, two plugins claiming the same name resolve by import order, and the frozen binary needs hidden-import hints. You have nine first-party formats; you don't need discovery. An explicit list in core (`PLUGINS = [csv, xlsx, ...]`) works frozen, works under the test runner, fails loudly on a broken import, and "every new format touches core" shrinks to one line. That probably deletes the build day and answers your second open question.

**3: what happens when the two validations disagree?** Splitting "format rules" from "schema rules" is a per-format judgment the script can't make, so someone draws that line nine times. Today's single pass produces one set of errors in one order; two passes will change which error a user sees first and may change the text. If anything downstream matches on those messages, that's a behavior change hiding inside a refactor. Also say whether core's check is the authority or a backstop, and what a backstop failure does: drop the row or abort the import.

**5: ignoring unknown keys keeps old callers working and makes new typos invisible.** `{"skip_hedaer": True}` silently does nothing. Have each plugin declare the keys it accepts, warn on unknowns during the flag window, reject after. A plain `dict` also gives mypy nothing; a TypedDict per plugin is cheap.

**6: two weeks only proves something if someone runs with the flag on.** Who, against what data? The real safety net is differential: run both paths on the same inputs and diff the rows, in CI, for the whole window. Then the calendar stops mattering. I'd also move one boring, well-tested format first and ship it alone. The migration script's blind spots show up on the first format, not the ninth, and a nine-format PR is hard to review well. Note the window also means every importer bug fix lands twice until the old path is removed; make that removal its own PR so there's a clean rollback point.

**The contract is missing.** Core owns the write path, but the note doesn't say what a plugin hands back: a generator of rows, a list, batches? How does a plugin skip a row, report a partial failure, or ask core to abort? That is the actual API, and it is the part that is expensive to change once nine plugins depend on it.

**On the open questions:** test ownership is an org question, but the design question under it is whether all nine formats have per-format tests today. If three were checked by hand, I'd guess coverage is uneven. List it per format before the PR, because the migration's safety rests on it.

**One meta question:** how often does a new format actually land? Twice a year and this is a lot of surface for the saving; monthly and the case makes itself. One sentence in the note either way.
