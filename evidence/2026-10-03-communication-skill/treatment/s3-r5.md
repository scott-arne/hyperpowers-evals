Item 4 is where I would push hardest, because its failure is silent. A format that keeps a module-level cache or mutates a class attribute between rows passes its own tests (one format per process) and produces wrong rows when two formats run in the same import, and the migration script moves it as-is. Check all nine before writing the script: grep each format's section of core for module-level mutables and for attributes assigned outside `__init__`. That takes an hour or two. Also say which three you checked; if they were the simplest formats, the sample says less than it looks like.

Item 2 causes both open questions and most of item 7's risk. A decorator only registers when its module is imported, so under the test runner's isolation, in the frozen binary, or after an import-order change, a format drops out of the registry with no error at import time, and the first sign is a job failing on a format that worked yesterday. Two changes close this. Have `plugins/__init__.py` import each plugin module by name, so discovery is an explicit list that behaves the same under pytest and when frozen (the cost per new format is one import line). Then have core assert after discovery that the registry holds the nine expected names, at least while the flag exists, to catch the case where the list is wrong. If the current plan is `pkgutil.walk_packages` or similar, that is the piece most likely to change behavior once frozen, and it is the reason to do the item 7 build work first and in its own PR: if the day turns into a week, you want to know before the plugin code exists.

Item 6's two weeks produces no evidence unless something runs the new path, and the note does not say who flips the flag. Since the new path is supposed to be output-identical, run both: parse with new, parse with old, diff the rows, write from old, log any diff. Two weeks of that gives a number: N imports across all nine formats, zero diffs. And if one of the formats from item 4 does keep state, the diff log is where it shows up first. Run the existing suite in CI with the flag in both positions for the same reason. While both paths exist, every importer bug fix lands twice.

Item 3 splits the current validation code by hand into format rules and schema rules, and the migration script cannot catch a rule that lands on neither side. List the rules in core today and check each appears exactly once after the split. Also decide what the caller sees when the plugin accepts a row and core rejects it: the same error as today, or a new type.

Item 5 makes a typo in an option name silent. `strict_mode` instead of `strict` runs the import non-strict and nothing says so. Ignore unknown keys during the flag window but log them; after the window, have each plugin declare its keys and reject the rest. The declaration doubles as the per-format options doc.

The test ownership answer depends on how the per-format tests are written today. If they go through core's public entry point, they do not move at all, and they are the tests that run in both flag positions above. If they call format functions directly, they move with the code and the owner is whoever owns the plugin.
