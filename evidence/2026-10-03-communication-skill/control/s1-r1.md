Found the cause of the nightly `ingest-orders` `DuplicateKeyError`. Reproduced locally.

Root cause

`pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time). `pipeline/writer.py` dedupes with `datetime.utcnow()`. In the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice. That is the roughly 1-in-4 pattern.

Two things kept it hidden:
- `utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`. The writer's first duplicate failures were swallowed and logged at DEBUG, so nothing surfaced until the unique index rejected a row.
- The CI schema-snapshot step passed on every failing night. The schema is not involved; it was never going to catch this.

Fix options

(a) Switch the orchestrator to UTC. One-line change, but 23 modules import `orchestrator.py`, so it moves the batch window for every stage. Needs a full suite run (about 25 min).
(b) Make the writer dedupe on local time. Stays inside one module, but keeps local time in the pipeline, which the team has wanted out since the March DST incident.

Recommendation

(a). It fixes the bug in the direction we already want to go; (b) leaves the local-time clock in place for the next incident.

One gap before I open that PR: I have not checked whether any of the 23 importers depend on the window being local time. That is about an hour of reading. I would rather spend it than learn the answer from a nightly run. Tell me if you want me to go ahead.

Separately, I'd flip the `retry()` default to `raise_on_exhaust=True` in its own PR. 14 call sites use the current default and some may rely on the swallow, so it needs its own review rather than riding along with the clock fix.
