Here's what I'd push on, roughly in order of how much it worries me.

**4 is the one that can hurt you.** "Assumed stateless, checked three of nine" is the load-bearing assumption for the whole migration and it is two-thirds unverified. Anything in core.py that is module-level today (a compiled regex, a cache, a counter, a connection handle, a `seen` set for dedup) is shared by all nine formats; after the split it is either duplicated per plugin or left in core where plugins can't see it. Either way behavior changes while the diff says "moved without changing it." I'd check all nine before sending this, or at least have the migration script list every module-level name each format's code touches. If the answer is "none," say so in the note; that's the sentence that makes the rest credible.

**5 hides bugs.** Ignoring unknown keys in `options` means `strict_mode` misspelled as `strictmode` silently runs non-strict, forever, with no error. "Old call sites keep working" is true but you can get that without silent-ignore: each plugin declares its known keys and core warns (or errors, after the compat window) on the rest. Old call sites only pass keys that exist today, so they pass the check.

**3 promises more than it delivers.** "A bad plugin cannot write a bad row" is only true if core's schema validation is already sufficient on its own. If it is, the plugin layer is a performance cost and a second place for rules to drift. If it isn't, the guarantee is false. Worth writing down what each layer actually checks. Also decide what happens when a row passes plugin validation and fails core: is that a plugin bug (fail the whole import loudly) or a data problem (skip and report)? Those are different code paths and different user experiences.

**2 and 7 are the same problem.** Registration by import-time side effect is why the frozen binary needs a build upgrade and why you don't know if it survives test isolation. Both go away if `plugins/__init__.py` just imports the nine modules explicitly, or holds a list. You lose "drop a file in and it works," but you were never going to have third-party plugins here, and you gain: the freezer sees ordinary imports (7 may shrink to zero), tests just import what they need, and a missing plugin is an ImportError at startup instead of a format that silently isn't registered. If you keep the decorator, make duplicate registration of a format name a hard error; last-wins is the kind of thing that bites a year from now.

**6: the flag is doing less than it looks like.** Default-old for two weeks means the new path gets zero production traffic unless someone flips it, and the note doesn't say who, for which formats, or what "done" looks like. Two weeks is a calendar, not evidence. A single global flag also means you can't ship the three formats you verified ahead of the six you haven't. I'd make it per-format, and I'd split the PR: build change + core + one format, then the rest in small PRs. Nine formats in one review is where reviewers skim. Also note that during the flag window core.py has both the old branches and the plugin dispatch, so any bug fix in that window has to land twice.

**7 is on the critical path and the estimate is soft.** Freezer plus dynamic import is exactly where "probably a day" turns into a week. Do it first as its own PR and prove discovery works in the actual frozen artifact before anyone writes a plugin. If it turns out hard, that's your answer on 2.

**Things the note doesn't say that the team will ask:**

- What's the plugin interface? The note gives `options: dict` but not the parse signature, the return type, or how a plugin reports a bad row. That contract is the design; the directory layout is a detail.
- Does the split move the transaction boundary? If the write path is in core and parsing is in the plugin, where does a mid-stream plugin exception leave the output?
- What's the forcing function? If a tenth format is coming, say so. If no new format has landed in a year, the team will reasonably ask whether this is worth the risk in 4.
- The test-ownership question shouldn't go to the team open. Propose a default (tests move with the code, owner is whoever owns the format today) and let people object.

Smallest version that still gets the benefit: explicit registration, per-format flag, one format in the first PR. Most of the risk above disappears with those three changes.
