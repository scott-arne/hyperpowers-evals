The duplicate writes happen because `pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time) while `pipeline/writer.py` dedupes with `datetime.utcnow()`. In the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice and the unique index rejects the second write. I recommend switching the orchestrator to UTC. Before that goes in I want about an hour to check whether any of the 23 modules that import the orchestrator depend on the window being local time; I have not done that check.

The writer's failures were hidden until the unique index caught them. `utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`, so the writer's exhausted retries were logged at DEBUG and otherwise dropped. I would change that default to `raise_on_exhaust=True` in its own PR: 14 call sites use the current default and several may depend on the swallow, so it needs its own review.

The two fixes:

- Switch the orchestrator to UTC. One line, and all 23 importers get the new window, so it needs the full suite (about 25 minutes).
- Make the writer dedupe on local time. Stays inside `pipeline/writer.py`, but keeps local time in the pipeline, which the team has wanted out since the DST incident in March.

Two things I ruled out: the schema check in `config/loader.py` and the one in `pipeline/writer.py` check the same thing and neither is involved, and the CI step that blocks deploy on a schema diff passed on every failing night.

Reproducing took about 40 minutes longer than it should have because `tests/conftest.py` pinned a `freezegun` that breaks under Python 3.12. I fixed the pin so the suite would run; that change is in the working tree.
