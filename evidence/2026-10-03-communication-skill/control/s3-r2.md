Direction is sane. Here's what I'd push on, in order of how much it worries me.

**The "stateless, moved without changing" claim carries the whole proposal and it's 3/9 verified.** If any of the other six keeps state across rows (a dedup set, a cached header, a running counter, an open handle), a mechanical move breaks it quietly. And "without changing" isn't quite true even for stateless code: if a format branch reads locals the core loop carries between iterations, lifting it into a function changes behavior. Before the PR, check all nine, and not by hand. Build a differential test: run old path and new path over the same fixture corpus and diff the output. That's cheap and it's the actual safety net. "I checked three" will not survive review of a nine-format PR, nor should it.

**Import-time decorator registration is the riskiest mechanism here, and it's also the only reason item 7 exists.** It depends on import order, it's fragile under test isolation (your own open question), and an import error in one plugin either takes down all nine or silently drops one depending on how discovery is written. Frozen builds are the kicker: they only bundle what they can see statically, so dynamically discovered modules get left out unless you list them as hidden imports, at which point you've written the explicit list anyway. So write it in core: `PLUGINS = [csv, xml, ...]`. Boring, deterministic, works in the frozen binary today, answers your second open question for free, deletes the day of build work. You lose "drop a file in and it registers," but these are nine internal formats, not a third-party ecosystem. Do you actually need discovery?

**The rollout doesn't give you a soak.** Flag defaults to the old path for two weeks means the new path gets zero traffic unless someone opts in. Who? Meanwhile core.py holds both the old branches and the plugin loop, so it's bigger during the flag window, not smaller, and any format fix has to land twice. I'd move one format per PR, new path on by default for that format, old branch deleted in the same PR, differential test as the merge gate. Rollback is a revert. You learn whether the mechanism works on format one before you've touched the other eight. If the one-PR-plus-flag shape is because deploys are hard to roll back, say so in the note; that changes the tradeoff.

**Double validation doesn't buy what the note says.** Core's schema check catches a plugin that emits a malformed row. It does not catch a plugin that maps the wrong source field into a valid column, which is the more likely migration bug. Keep it, but don't sell it as "a bad plugin cannot write a bad row." Also, today format rules and schema rules are interleaved in one place; someone has to split them, and that split is a behavior change, not a move.

**`options: dict` with unknown keys ignored means typos do nothing.** `delimeter=";"` imports fine with the wrong delimiter. At minimum log unknown keys. Better, each plugin declares what it accepts and the new path rejects the rest. Any old call site that passes junk today is already misconfigured; you'd just find out.

Smaller:

- Where does field mapping live? You list it as something core holds today, then only say "format-specific" moves. Mapping is half format, half schema. Decide before the migration script runs.
- What does a plugin return? If core streams today and a plugin materializes a list, large files regress. Pin the interface in the note.
- Are all nine formats alive? If a couple have no users, delete them instead of migrating them.
- Test ownership: settle it before the split, and confirm per-format tests exist before code moves. If they don't, the ownership question is moot because there's nothing to own.

The question I'd want answered before any of this: what's the actual pain? If it's "adding a format is annoying," how often does that happen? If it's "core.py is unreadable and hard to test," one module per format with an explicit list gets you most of the way with no decorator, no build change, and no flag.
