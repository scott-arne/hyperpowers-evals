The two I would push on hardest are the stateless assumption in 4, because the script will move six formats nobody has checked, and the import-time registration in 2, because it is the cause of both the frozen-binary work in 7 and the test-isolation question at the end.

Item 4 is only safe if none of the nine modules has module-level state. Three are checked, six are not. A module-level cache, a regex object that gets mutated, a counter, a parser instance shared across calls: any of these behaves differently once it lives in a module that discovery imports once, outside the flow of core. I would check the other six before writing the migration script, or have the script refuse to move a module with mutable module-level names.

Item 2 makes the registry depend on who imported what and when. That is why it breaks under a test runner that isolates imports (the registry comes up empty, or with duplicates), and why the frozen binary cannot find the package (nothing imports it, so the freezer never bundles it). If core imports each plugin by name from an explicit list, both problems go away: the freezer and the test runner both see ordinary imports, and the day in 7 is probably unnecessary. What you give up is adding a format without touching core, which is one line in a list.

Item 5 keeps old call sites working, and it also means a misspelled option name does nothing and nobody is told. It hides the case where core used to honor an option that the plugin now drops. I would warn on unknown keys from the start and have each plugin declare the keys it reads.

Item 3 claims a bad plugin cannot write a bad row. The core check catches a row that violates the schema. A row that is schema-valid and wrong, which is what a mis-mapped column produces, passes. Say "schema-invalid" so the team does not read it as a correctness guarantee. Also define what happens when core rejects a row the plugin accepted (skip the row, fail the batch), whether that matches the old path today, and what validating twice costs on the largest import.

Item 6 defaults the flag to the old path, so the new path gets no traffic unless someone flips it. The two weeks only start counting once a format is actually running the new code. I would make the flag per format, flip one low-volume format first, and for at least one format run both paths and diff the rows before writing (writing the old result). Nine formats in one PR is also too much to review line by line; the core split plus one format is reviewable, and the other eight are mechanical after that.

Field mapping is not in the note. Core today holds the loop, the mapping, the validation, and the write path. Item 1 keeps the loop and the write path, item 3 covers validation, and the mapping is unaccounted for. If it is one shared table today, splitting it into nine copies is a regression. If it is already per format, say so.

For the tests question, move each format's tests into the same PR as its plugin, so a plugin with no tests cannot land. Ownership then follows the file.

One more the team will ask: what does a plugin receive and return? The note has the registration mechanism and the options dict, and nothing about the call signature, whether a plugin yields rows or returns a list, or how it reports a parse error partway through a file.
