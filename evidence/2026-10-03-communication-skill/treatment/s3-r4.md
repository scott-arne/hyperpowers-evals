The two I'd fix before it goes out: the stateless claim in 4, and the discovery mechanism in 2, which is also what makes 7 and the second open question hard.

Item 4 rests on three of nine formats checked. The move is mechanical only if all nine are stateless, and the six unchecked ones are where the team will push. Before the PR, go through those six for module-level mutable state, writes to `self` outside `__init__`, and anything in core's loop shared across formats (a dedup set, a running counter, an open handle). One hit means that format's code changes when it moves, and "without changing it" comes out of the note. If you keep the claim, say which three you checked.

Item 2, discovery by importing the package, causes three separate problems in the note. In a frozen binary, the freezer only sees modules reached by a static import, so each plugin has to be declared to it by hand (hidden imports, in PyInstaller's terms); that is the work in 7, and the estimate I trust least in the plan. Under the test runner's import isolation, a decorator that runs at import time registers once per import: if the runner reloads core while `sys.modules` still holds the plugins, the new registry is empty, and if it reloads both, every format registers twice. And a syntax error in one plugin fails the package import, so all nine formats disappear together. An explicit list of module names in core, imported by core, with no import-time registration, removes all three: the freezer sees static imports, the test runner sees ordinary imports, and a broken plugin fails on its own line. Nothing is lost, since the plugins are in-repo and nobody adds one without touching core. It may also make 7 unnecessary; check that before spending the day.

Item 3 needs one more sentence. Validation is one block in core today. Splitting it into format rules and schema rules means classifying every existing check, and some will be both or neither. Any check that moves into a plugin because it looked format-specific leaves core's pass weaker than today's single pass, so "a bad plugin cannot write a bad row" holds only for what core's pass covers. Enumerate the current checks with a side for each, so the team reviews a list.

Item 5: with unknown keys ignored, a typo in an option name does nothing and the import runs with defaults. If the point is that old call sites keep passing keys the new plugin does not use, warn on unknown keys during the flag period, then raise. Also say how the old call sites become dict-passing ones; if they pass keyword arguments to specific functions today, that is an edit at every call site, and it is not in the note.

Item 6: with the flag at its default, nothing runs the new path. Say who flips it, in which environment, and what gets compared. The cheap version is to run both paths on the same input in CI and diff the written rows; two weeks of that is the signal the flag period is supposed to produce. During those two weeks every importer bug fix lands in two places, the branch in core and the plugin. And one PR for nine formats fixes the plugin API before anyone but you has written against it. Moving one format first (one of the three you checked), shipping it, then the other eight, adds one PR cycle and gives the team a PR they can read and an API that has been used once.

Open question 1 should carry your proposed answer. Left open, the meeting decides it; proposing "the format owner, same as today" and asking for objections is faster.

Two things someone will ask that the note does not say: what a plugin hands back to core (rows one at a time, a batch, an iterator), and where errors surface after the split, since today they come out of core with the format attached.

Last, the motivation. "Every new format means another branch in core" is true; how often does a new format arrive? If it is one a year, the team will ask whether the migration plus the build change pays back, and the note should answer that before they do.
