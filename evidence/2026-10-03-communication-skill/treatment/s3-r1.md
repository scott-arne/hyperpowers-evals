The two things I'd push on hardest are item 4 and the pairing of items 2 and 7. The rest are smaller.

Item 4. Six of the nine formats are unchecked for state, and the "move without changing" claim rests on all nine being stateless. If one keeps state across rows (a header read on row one, a lookup built as it goes), it works today because core runs it once per file, and it can go wrong quietly once core holds one instance and reuses it. Check the other six before the PR goes up, and name the three you checked in the note. It is a few minutes per format and the team will ask.

Items 2 and 7 together. The day of build work exists only because discovery imports the package and the frozen binary cannot find it. An explicit table in core (format name to module, nine lines) gives you the same split with no build change, works under the test runner's import isolation, and answers your second open question. It costs one line in core per new format, which is less than the branch the proposal is removing. If you keep the decorator, two things to add: raise on duplicate registration (today the last import wins and nothing says so), and decide what happens when one plugin fails to import, because with package-import discovery one broken plugin makes the package import fail and none of the nine registers.

Item 3. Splitting the current validation into format rules and schema rules is a judgment call per rule, so that part of the move is not mechanical even for the stateless formats. State which existing checks go where. Also check the cost: every row through two validators may matter on the big imports.

Item 5. Ignoring unknown keys means a typo in an option name does nothing and nobody is told. Log unknown keys at warning level at least, so old call sites keep working and the next person who misspells `delimiter` finds out.

Item 6. A flag that defaults to the old path for two weeks produces no evidence unless something runs the new path during those two weeks. Say who turns it on, for which formats, and what you compare before flipping the default. The cheap version: run both paths on the same inputs and diff the written rows, for every format, before the PR merges. That also gives the migration script the regression check it otherwise lacks. One PR for all nine also means two copies of every format's code for the two weeks, so any format fix in that window goes in twice. Per-format flags, or several smaller PRs, would let you move the three you have checked first.

Two things the note does not cover. Where the shared field mapping goes if two or more formats use the same helpers: "everything format-specific moves to the plugin" either duplicates it or leaves it in core, and the note should say which. And what core does when a plugin raises mid-file: whether it stops, skips the row, or rolls back the write, and whether that matches what happens today.

On the test ownership question: before deciding who owns them, check whether the current per-format tests run through core's loop and write path. If they do, they are your before/after check for the whole migration and should stay green unchanged across the move. If they only call the format functions directly, nothing checks that the move preserved behavior, which matters more than ownership.
