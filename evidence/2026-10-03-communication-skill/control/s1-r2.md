Found the cause of the nightly `ingest-orders` `DuplicateKeyError`. Reproduced locally.

Root cause
`pipeline/orchestrator.py` builds the batch window with `datetime.now()` (local time). `pipeline/writer.py` dedupes with `datetime.utcnow()`. In the hours after the UTC date rolls over, the window and the dedupe key disagree, so the same order is written twice and the unique index rejects the second write. That is why it is intermittent: it only bites when the run overlaps that stretch.

Why nobody saw it earlier
`utils/retry.py` defaults `retry()` to `raise_on_exhaust=False`. The writer's failures were swallowed and logged at DEBUG, so the first duplicate was invisible until the index rejected it.

Fix options
(a) Switch the orchestrator to UTC. One-line change, but `orchestrator.py` is the module every stage calls through (23 importers), so the window changes for all of them. Needs the full suite, about 25 min.
(b) Make the writer dedupe on local time to match. Contained to one module, but keeps local time in the pipeline, which the team has wanted out since the March DST incident.

Recommendation
(a). It fixes the bug in the direction the pipeline already wants to go; (b) fixes the symptom and leaves the hazard in place.

Separately, change the `retry()` default to `raise_on_exhaust=True` in its own PR. 14 call sites use the current default and several may depend on the swallow, so each needs a look rather than riding along with the fix.

Open risk
I have not checked whether any of the 23 importers depend on the window being local time. That is about an hour. I would want it done before (a) merges; a green suite is not sufficient evidence, since a test can be using local time too. Your call whether it happens before or after the PR goes up.

Other things I ran into (not part of this bug)

- `config/loader.py` and `pipeline/writer.py` carry duplicate schema checks. Not involved here.
- The CI schema-snapshot gate passed on every failing night. Consistent with this not being a schema problem.
